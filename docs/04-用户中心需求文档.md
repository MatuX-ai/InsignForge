# InsightForge 个人版 —— 用户中心需求文档

**版本**：v1.0  
**最后更新**：2026年8月  


## 一、概述

### 1.1 文档目的

本文档定义 InsightForge 个人版用户中心的功能需求、技术方案和集成方式。用户中心基于 **Casdoor** 构建，作为独立的身份认证与访问管理（IAM）服务，为 InsightForge 提供用户注册、登录、权限管理和账号安全等全套能力。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **独立部署** | Casdoor 作为独立服务运行，与 InsightForge 主应用解耦 |
| **开箱即用** | 个人版部署即自带用户中心，无需额外配置 |
| **安全优先** | 密码加密存储、支持多因素认证、登录审计 |
| **渐进增强** | 个人版先用基础功能，为团队版预留扩展能力 |

### 1.3 与产品定位的关系

个人版的核心是“单用户本地工具”，用户中心的存在不是为了制造登录门槛，而是：

1. **为未来的团队版做准备**——个人版积累的用户数据可无缝迁移
2. **保护本地数据**——多用户共用一台机器时，数据互不可见
3. **提供社交登录便利**——可用 GitHub/Google 账号快速登录，无需额外注册

|----------|----------|--------|

| UR-02 | 支持通过 GitHub、Google 等第三方账号登录注册 | P1 |
| UR-03 | 注册时校验邮箱格式、密码复杂度（至少8位，含字母和数字） | P0 |
| UR-04 | 注册成功后自动登录并跳转至首页 | P0 |

### 2.2 用户登录

| 需求编号 | 需求描述 | 优先级 |
|----------|----------|--------|
| UL-01 | 支持邮箱+密码登录 | P0 |

| UL-03 | 登录失败提示（统一提示“邮箱或密码错误”，不暴露具体原因） | P0 |

## 三、非功能需求

| 需求编号 | 需求描述 | 指标 |
|----------|----------|------|
| NFR-01 | 登录接口响应时间 | ≤ 500ms |
| NFR-02 | 用户中心服务可用性 | 99.5%（个人版单机部署） |
| NFR-03 | 密码加密强度 | bcrypt cost factor ≥ 10 |
| NFR-04 | Token 签名算法 | RS256 或 HS256 |
| NFR-05 | 支持部署方式 | Docker Compose 一键启动 |
| NFR-06 | 数据库 | 独立 PostgreSQL，与主应用数据库隔离 |


## 四、技术方案

### 4.1 整体架构

InsightForge 用户中心基于 Casdoor 构建，作为独立服务部署：

```
┌─────────────────────────────────────────────────────────────────┐
│                      InsightForge 用户                         │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                   Casdoor (独立服务)                           │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐           │
│  │  登录页面   │  │  用户管理   │  │  权限管理   │           │
│  │  (托管UI)   │  │  (API)      │  │  (RBAC)     │           │
│  └─────────────┘  └─────────────┘  └─────────────┘           │
│  端口: 8000                                                    │
└─────────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
│  InsightForge   │ │  InsightForge   │ │  PostgreSQL     │
│  前端 (React)   │ │  后端 (Node.js) │ │  (用户数据)     │
│  端口: 3000     │ │  端口: 3001     │ │                 │
└─────────────────┘ └─────────────────┘ └─────────────────┘
```

### 4.2 Casdoor 部署

```bash
# 使用 Docker Compose 部署 Casdoor
version: '3.8'
services:
  casdoor:
    image: casbin/casdoor:latest
    ports:
      - "8000:8000"
    environment:
      - RUNNING_IN_DOCKER=true
      - dataSourceName=postgres://casdoor:password@postgres:5432/casdoor
    depends_on:
      - postgres

  postgres:
    image: postgres:15
    environment:
      - POSTGRES_DB=casdoor
      - POSTGRES_USER=casdoor
      - POSTGRES_PASSWORD=password
    volumes:
      - ./casdoor-data:/var/lib/postgresql/data
```

### 4.3 认证流程

**登录流程**：

1. 用户访问 InsightForge 前端，点击“登录”
2. 前端跳转至 Casdoor 登录页面（`http://casdoor:8000/login`）
3. 用户完成登录，Casdoor 回调前端并携带 `code`
4. 前端将 `code` 发送至 InsightForge 后端
5. 后端使用 Casdoor SDK 换取 `access_token` 和用户信息
6. 后端生成自有 JWT 返回前端，前端存储 Token

**API 鉴权流程**：

1. 前端在 HTTP Header 中携带 `Authorization: Bearer <token>`
2. 后端中间件验证 Token 有效性
3. 从 Token 中解析 `user_id`，注入请求上下文
4. 业务逻辑根据 `user_id` 操作对应数据

### 4.4 数据同步

| 数据类型 | 存储位置 | 同步方式 |
|----------|----------|----------|
| 用户身份信息（ID、邮箱、昵称） | Casdoor 数据库 | 登录时从 Casdoor 同步到本地 `users` 表 |
| 用户设置（偏好、配置） | InsightForge 本地数据库 | 由 InsightForge 自行管理 |
| 用户项目数据 | InsightForge 本地数据库 | 通过 `user_id` 关联 |

**同步时机**：
- 用户首次登录时，在本地 `users` 表创建记录
- 每次登录时，更新本地用户信息（昵称、头像等）
- Casdoor 中用户信息变更时，通过 Webhook 通知 InsightForge（团队版）

### 4.5 与 InsightForge 的接口

InsightForge 后端需实现以下与 Casdoor 交互的接口：

| 接口 | 方法 | 说明 |
|------|------|------|
| `/auth/callback` | POST | 接收 Casdoor 回调的 code，换取 token |
| `/auth/logout` | POST | 清除本地会话，可选同时登出 Casdoor |
| `/auth/user` | GET | 获取当前登录用户信息 |
| `/auth/verify` | GET | 验证 Token 有效性（中间件内部调用） |

### 4.6 目录结构（后端）

```

├── auth/
│   ├── casdoor.ts          # Casdoor SDK 封装
│   ├── middleware.ts       # JWT 验证中间件
```

## 五、用户数据模型

### 5.1 Casdoor 用户模型

Casdoor 内置用户模型，包含但不限于以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 用户唯一标识 |
| `name` | string | 用户名 |
| `displayName` | string | 显示名称 |
| `email` | string | 邮箱 |
| `phone` | string | 手机号 |
| `avatar` | string | 头像 URL |
| `password` | string | 加密密码 |
| `createdTime` | string | 创建时间 |
| `updatedTime` | string | 更新时间 |

### 5.2 InsightForge 本地用户表

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    casdoor_id VARCHAR(64) UNIQUE NOT NULL,   -- Casdoor 用户 ID
    email VARCHAR(255) NOT NULL,
    name VARCHAR(100),
    avatar_url TEXT,
    plan_type VARCHAR(20) DEFAULT 'free',      -- free / pro / team
    settings JSONB DEFAULT '{}',               -- 用户偏好设置
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_users_casdoor_id ON users(casdoor_id);
CREATE INDEX idx_users_email ON users(email);
```

## 七、安全要求

| 要求编号 | 要求描述 | 实现方式 |
|----------|----------|----------|
| SEC-01 | 密码不以明文传输 | HTTPS + 密码加密传输 |
| SEC-02 | 密码不以明文存储 | bcrypt 加密 |
| SEC-03 | Token 防篡改 | JWT 签名验证 |
| SEC-04 | 防止 CSRF 攻击 | 使用 SameSite Cookie 或 CSRF Token |
| SEC-05 | 登录失败限流 | 连续失败 5 次后锁定 15 分钟 |
| SEC-06 | 会话超时 | Token 有效期 24 小时 |

## 九、常见问题

**Q1：个人版一定要登录才能用吗？**

A：是的。登录是为了保护用户数据（项目、报告、配置）不被他人访问。但 v1.0 仅支持本地部署，不存在“云端账号”的概念，所有数据仍存储在本地。

**Q2：Casdoor 部署失败怎么办？**

A：Casdoor 提供 Docker 一键部署，如果遇到问题，可查看 Casdoor 官方文档或 GitHub Issues。InsightForge 安装脚本会检测 Casdoor 是否正常运行。

**Q3：可以不用 Casdoor，自己写用户中心吗？**

A：可以，但不推荐。Casdoor 提供了完整的用户管理、认证、安全能力，自行实现需要投入大量精力处理密码加密、会话管理、安全防护等细节，且未来扩展团队版时仍需要迁移到 Casdoor。

**Q4：Casdoor 和 InsightForge 的数据如何保持一致？**

A：Casdoor 是用户身份的权威来源，InsightForge 本地 `users` 表是缓存和扩展。登录时从 Casdoor 同步最新信息，用户的项目数据通过 `casdoor_id` 关联，不存在数据不一致的问题。
