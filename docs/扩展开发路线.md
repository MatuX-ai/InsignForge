# InsightForge —— 扩展开发路线图

**版本**:v1.3 Draft
**最后更新**:2026年8月
**文档状态**:路线图(v1.3 → v2.0)
**适用范围**:InsightForge 个人版 / 桌面版 / dsh 插件 / MCP Server 共享同一采集内核


## 一、文档概述

### 1.1 目的

本文档规划从 v1.3 至 v2.0 的扩展开发路径,围绕多源采集引擎这一核心模块,从可观测性、智能化、数据源扩张、平台化四个维度展开。每个阶段给出**目标、关键任务、验收标准、技术取舍**,便于团队按节奏推进,避免一次性大改带来的回归风险。

### 1.2 阅读指南

| 读者角色 | 建议阅读章节 |
|---------|-------------|
| **架构师** | 二、当前基线;三、路线原则;七、关键决策 |

### 1.3 关键约定

- **零外部依赖优先**:能本地实现的就不引 npm 依赖;确需引入需在决策表说明理由
- **不破坏调用方**:新能力以"叠加"形式存在,老路径行为不变
- **每阶段可独立发布**:v1.3 / v1.4 / v1.5 / v2.0 都能单独 ship,失败不互相阻塞
- **每阶段带量化验收**:覆盖测试数、缓存命中率、平均延迟、失败率等可观测指标


## 二、当前基线(已完成)

### 2.1 v1.2 → v1.3 健壮性增强

| 维度 | 改造前 | 改造后 |
|------|-------|-------|
| 重试 | 单次失败即放弃 | 指数退避 2 次,仅对 5xx/429/网络错重试 |
| 熔断 | 无;持续失败仍持续打 | 每源连续 5 败自动开 30s,半开探测恢复 |
| 缓存 | 无;同关键词重复打外网 | 每源 TTL 5min(OpenSerp/SerpApi 按 engine+keyword) |
| 并发 | `keywords.map(async)` 全并行 | 关键词维度 `KEYWORD_CONCURRENCY=3` 信号量限流 |
| 去重 | URL 精确匹配;utm/`#`/大小写视为不同 | URL 归一化 + 无 url 走 title+source 指纹 |
| 错误 | `err` 直接 warn,无分类 | 8 类 `SourceError.kind`,按 retryable 决定是否重试 |
| 指标 | 无 | 每源 success/failure/successRate/avgLatencyMs/failureByKind/cacheHits/circuitOpened |

## 三、路线原则

1. **可观测性 > 智能化 > 多源扩张 > 平台化** — 先把"看得见的稳"做扎实,再做"看不见的聪明"
2. **沿用 reliability 基座模板** — 所有新源/新能力都套 `withReliability(source, cacheKey, fn)`,避免重新发明
3. **不破坏调用方** — 新增能力以"叠加"形式存在,老路径行为不变
4. **每阶段可独立发布** — 任何阶段失败不阻塞前序版本
5. **每阶段带可量化验收** — 覆盖测试数、缓存命中率、平均延迟、失败率
6. **风险先验** — 反爬严 / 鉴权复杂的源(Product Hunt OAuth、中文知乎/微博)放在后期


## 四、阶段任务

### 阶段 1 · v1.3:可观测性 + 用户可控性(1-2 周)

> **目标:把"看不见的内部状态"翻译成"用户和管理员能感知的能力"**

#### 1.1 健康检查 API

- 新增 `backend/src/api/health.ts`,挂载到 `GET /api/v1/health/sources`
- 直接返回 `sourceMetrics.snapshot()`,字段:
  ```ts
  { source, success, failure, successRate, avgLatencyMs,
    failureByKind, cacheHits, circuitOpened, state }
  ```
- 鉴权:仅桌面模式或管理员可访问(避免外网扫描)
- **验收**:curl 返回 4 个源快照;熔断打开时 `state: 'open'` 立即可见

#### 1.2 失败重试 UI

- 前端项目页加"重新触发调研"按钮(复用 `ExecutionService.triggerResearch`)
- 失败原因展示:把 `SourceError.kind` 翻译为可读中文,例如:
  - `rate_limit` → "搜索引擎限流,请稍后重试或切换 SerpAPI"
  - `circuit_open` → "源暂时不可用,已自动跳过"
  - `client_4xx` → "鉴权失败,请检查 API Key"
- 进度条 + 当前 step 文案(已有 `current_step` 机制,无需重构)
- **验收**:用户可一键重试且看到上次失败原因

#### 1.3 持久化缓存(可选,数据驱动)

- 把 `reliability.ts` 的 `TtlCache` 升级为 `SqliteTtlCache`(落到 SQLite 的 `search_cache` 表)
- 跨进程保留 24h,重启不丢
- **决策**:先用内存缓存跑数据看命中率,>30% 才投入持久化
- 避免过早优化

#### 1.4 测试清理 + 覆盖率门槛

- 修 `dedupe.test.ts` 中 `'g' as const` typo → `'google' as const`(与 `MarketNeedSource` 一致)
- 把 `search/` 加入 vitest 覆盖率统计,`vitest.config.ts` 加:
  ```ts
  include: [...existing,
    'src/services/search/reliability.ts',
    'src/services/search/dedupe.ts',
    'src/services/search/Aggregator.ts']
  ```
- 阈值:`lines: 80`
- **验收**:`search/` 目录覆盖率 ≥ 80%


### 阶段 2 · v1.4:智能化增强(2-3 周)

> **目标:从"机械聚合"升级到"语义理解 + 智能打分"**

#### 2.1 标题语义去重

- 在 `dedupe.ts` 新增 `semanticKey(title, source)`:title 转小写 → tokenize → Jaccard 相似度
- 阈值 0.7 视为同一条;可选 LLM 重判(成本敏感,默认关闭)
- 双层去重:先 URL 归一化 → 再语义指纹
- **验收**:相同事件多源报道(如 HN/Reddit 都讨论"X 公司裁员")合并为 1 条

#### 2.2 LLM 重排序

- 在 Aggregator 之后加 `llmRerank(items, idea, top=30)`
- 让 LLM 按"与 idea 的相关性 / 信源权威 / 新鲜度"重新打分
- 复用现有 `chatCompleteWithSchemaRetry`,schema:
  ```ts
  { id: string, relevance: 0-10, freshness: 0-10,
    authority: 0-10, score: 0-10 }
  ```
- **验收**:top 30 排序后,前 10 与人工标注相关性 ≥ 80%

#### 2.3 痛点抽取

- 在 ReportService 流程加 `extractPainPoints(market_needs)` → top 10 痛点
- 输入:聚合后的 100 条原始数据
- 输出:`string[]`,去重 + 按提及频次排序
- **验收**:抽取结果与人工标注重合度 ≥ 70%

#### 2.4 自动关键词扩展

- 在 MarketResearcher.extractKeywords 后接 `expandKeywords(seeds)` → 长尾词 5-10 个
- 用 LLM 基于种子关键词生成同义词 / 相关词
- **验收**:扩展词与原始关键词 Jaccard < 0.5,且能带来 ≥ 20% 新数据


### 阶段 3 · v1.5:数据源扩张(3-4 周)

> **目标:把多源从 4 个扩展到 8-10 个,覆盖技术 / 消费 / 学术**

| 数据源 | 类型 | 接入难度 | 风险点 | 优先级 |
|--------|------|----------|--------|--------|
| Product Hunt | GraphQL API | 中 | 需 OAuth Token | P0 |
| GitHub Issues/Discussions | GraphQL API | 低 | 需 PAT | P0 |
| App Store 评论 | HTML + JS 渲染 | 中 | 反爬绕过 | P1 |
| Google Play 评论 | HTML + JS 渲染 | 中 | 反爬绕过 | P1 |
| arXiv | 公开 API | 低 | 字段简单 | P1 |
| Stack Overflow | 公开 API | 低 | 限流严 | P2 |

#### 3.1 Product Hunt(优先级最高)

- API:`https://api.producthunt.com/v2/api/graphql`(需 OAuth Token)
- 字段映射:name / tagline / url / votesCount / commentsCount / createdAt
- 走 reliability 基座,cacheKey: `producthunt:${hashKey(kw|date)}`
- **风险**:需引导用户配置 PH Token(设置页扩展)

#### 3.2 GitHub Issues / Discussions

- GraphQL API:`https://api.github.com/graphql`(需 PAT)
- 字段:title / body / comments / reactions / state
- 面向 B2B / 开发者工具的痛点发现
- **验收**:repo + query 检索成功率 ≥ 95%

#### 3.3 App Store / Google Play 评论

- 接入 Crawlee + Playwright(`crawler/` 已预留扩展点)
- 客户端传 appId,爬取最近 50 条评论
- 中等复杂度:反爬绕过 / 渲染等待
- **验收**:单 app 拉取成功率 ≥ 90%

#### 3.4 arXiv(学术研究)

- API:`http://export.arxiv.org/api/query`
- 字段:title / abstract / authors / categories
- 面向科研 / AI 工具的早期信号
- **验收**:检索延迟 < 2s

#### 3.5 Stack Overflow

- 公开 API,免费但有配额
- 面向开发者痛点
- **验收**:仅在 v1.5 末位,看时间余量决定是否做


### 阶段 4 · v2.0:平台化 + 中文生态(1-2 月)

> **目标:从"工具"到"平台",从"英文"到"中英双语"**

#### 4.1 WebSocket / SSE 实时进度推送

- 替代 `getResearchStatus` 轮询
- 优先选 **SSE(EventSource)** 而非 WebSocket(单向推送,SSE 自动重连更简单)
- 事件:`step_change` / `item_collected` / `source_failed` / `done`
- 前端 EventSource 接收,UI 实时刷新
- **验收**:100ms 内 step 变更可见;断线自动重连

#### 4.2 MCP server v2

- 把 `search/*` + `MarketResearcher` 全部 tools 化
- 已有 `packages/mcp-server/` 框架;扩展 tools 注册表
- 工具列表:
  - `market_research`(已有)
  - `competitor_analysis`(已有)
  - `product_hunt_search`(新增)
  - `github_search`(新增)
  - `arxiv_search`(新增)
- **验收**:Claude / Cursor 通过 MCP 可完成"市场调研 → 报告生成"全流程

#### 4.3 用户中心 + 共享需求池

- 多用户场景(虽然 MVP 是单人)
- 复用 `docs/04-用户中心需求文档.md` 设计
- **验收**:用户登录 / 项目共享 / 协作标注

#### 4.4 中文源接入 + 双语支持

- 知乎 / 微博 / 微信公众号(搜狗代理)
- LLM 翻译:英文检索结果 → 翻译为中文展示
- **风险最高**:中文反爬严、鉴权复杂,独立子项目
- **验收**:中文源占比 ≥ 30%(中文用户场景)


## 五、阶段依赖图

```
        v1.3 (可观测性)
              │
              ├──→ v1.4 (智能化) ──→ v1.5 (多源扩张) ──→ v2.0 (平台化)
              │              │              │
              └──────────────┴──────────────┴──→ 后续:v2.1+ AI Agent 化
```

依赖说明:
- v1.4 依赖 v1.3 的指标 API(LLM 重排序需要观测耗时与成功率)
- v1.5 依赖 v1.4 的语义去重(多源同时接入时去重压力更大)
- v2.0 依赖前三阶段的所有基座(平台化是聚合而非新建)

## 七、关键决策与取舍

| 决策点 | 选择 | 拒绝方案 | 理由 |
|--------|------|----------|------|
| 缓存层 | 进程内 → 数据量起来后升 SQLite | 一开始就用 Redis | 单人 MVP,Redis 是过度工程 |
| 语义去重算法 | Jaccard token 阈值 0.7 | embedding + 向量库 | embedding 依赖外部 API 且延迟高,Jaccard 零成本 |
| LLM 重排序 | 复用 `chatCompleteWithSchemaRetry` | 新建独立打分服务 | 已有重试机制和 schema 校验,没必要造轮子 |
| 中文源顺序 | 最后做(v2.0) | 与英文源并行 | 中文反爬严,先把英文结构化源做扎实 |
| 实时推送 | SSE(EventSource) | WebSocket | 调研是单向推送,SSE 更简单且自动重连 |
| 持久化缓存 | 命中率 > 30% 才升 | 默认升 | 避免过早优化 |
| MCP server | 在 v2.0 全面 tools 化 | 一开始就 MCP-only | 桌面/Web 是主要用户,MCP 是增量 |
| 用户中心 | v2.0 单独立项 | 与 v1.5 并行 | 多用户会引入鉴权/并发/隔离,改架构风险高 |
