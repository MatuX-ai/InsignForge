# InsightForge 个人版 —— 前端设计文档

**版本**：v1.0  
**最后更新**：2026年8月  


## 一、设计目标

### 1.1 核心原则

这个产品是给创业者、产品经理自己用的工具，不是给大众消费的娱乐产品。设计上遵循几个朴素的原则：

- **功能优先于花哨**：用户打开页面是为了验证想法、看报告，不是为了欣赏动画
- **减少认知负担**：整个产品只做一件事——输入想法，看报告。不要让用户思考“我该点什么”
- **数据可读性**：报告是核心产出，所有设计围绕让报告好读、好理解展开
- **本地工具感**：这不是一个“云平台”，更像一个装在电脑里的专业工具，不需要登录、不需要 onboarding 流程

### 1.2 与同类产品的区别

| | Notion | 传统调研报告 | InsightForge |
|---|---|---|---|
| 交互方式 | 自由编辑 | 静态阅读 | 输入→生成→阅读 |
| 数据来源 | 用户手动输入 | 人工整理 | 系统自动采集 |
| 用户预期 | 写东西的地方 | 看东西的地方 | 验证想法的地方 |

InsightForge 的界面更像“傻瓜相机”——按一下快门，照片出来。不需要调参数。


## 二、整体布局

### 2.1 页面结构

整个应用只有三个核心视图，用顶部简易导航切换：

```
┌─────────────────────────────────────────────────────────────────┐
│  InsightForge        [首页]  [历史]  [设置]                    │  ← 顶部栏
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│                         页面内容区域                             │  ← 主内容区
│                                                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

顶部栏高度 56px，内容区填满剩余视口高度。

### 2.2 响应式断点

| 断点 | 宽度 | 布局调整 |
|------|------|----------|
| 桌面 | ≥1024px | 完整布局，报告双栏展示 |
| 平板 | 768-1023px | 报告单栏，边距缩小 |
| 移动 | <768px | 全屏单栏，顶部栏折叠 |

移动端不是优先目标，但需要保证可读性。早期用户主要是在电脑前工作的创业者。

### 2.3 颜色

不做花哨的渐变色和毛玻璃效果。

```
主色：#2563EB     // 偏沉稳的蓝，用于主按钮和链接
成功：#16A34A     // 仅用于“已完成”状态标记
警告：#D97706     // 用于等待状态
文本主：#111827    // 接近黑色，保证阅读舒适度
文本次：#6B7280    // 辅助信息
背景：#F8FAFC     // 极浅灰，比纯白护眼
卡片：#FFFFFF      // 纯白
边框：#E5E7EB     // 极浅灰边框
```

字体用系统默认栈，不加自定义字体：

```css
font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif;
```

文字大小层级：

| 用途 | 大小 | 字重 |
|------|------|------|
| 页面标题 | 24px | 600 |
| 区块标题 | 18px | 600 |
| 正文 | 15px | 400 |
| 辅助文字 | 13px | 400 |
| 小标签 | 12px | 500 |


## 三、页面设计

### 3.1 首页（核心页面）

首页只做一件事：接收输入，触发调研。

**布局**（垂直居中）：

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│                                                                 │
│                    InsightForge                                 │
│                                                                 │
│              ┌─────────────────────────────────────┐           │
│              │  输入你的产品想法...                  │           │
│              └─────────────────────────────────────┘           │
│                                                                 │
│                    [ 验证想法 ]                                 │
│                                                                 │
│              或者从需求库找灵感 →                               │
│                                                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

输入框是多行文本（textarea），高度约 120px，可手动拖拽调整。占位文字提示用户输入什么，比如：

> 描述你想验证的产品或功能，例如：“一个帮助程序员远程结对编程的 VS Code 插件”

输入框下方放一个示例按钮，点一下自动填入示例文本，方便用户快速体验。

**状态变化**：

- 输入为空时，“验证想法”按钮置灰不可点
- 输入有效时，按钮变为可点
- 点击后，按钮文字变为“分析中...”，加一个简单的 loading 指示（不是转圈动画，用三个点闪烁，更像命令行风格）
- 分析完成后，页面自动滚动到报告区域

没有复杂的 onboarding、没有弹窗、没有教程。用户自己会试。

**设计细节**：

- 每个卡片有标题和内容，卡片间用 24px 间距
- 数字指标用大号字体（32px）展示，便于扫读
- 竞品和痛点用列表展示，每条带一个浅色圆点标记
- 数据来源链接用蓝色文字，可点击跳转
- 最下方“生成验证页”按钮是次要操作，用线框样式（outline button）

报告加载时，不展示骨架屏，直接展示一个带进度描述的 loading 状态，比如“正在搜索竞品信息...”、“正在分析用户反馈...”。给用户一种“正在干活”的感觉。

## 四、交互细节

### 4.1 反馈机制

用户操作需要明确的反馈，但不需要弹窗。

| 操作 | 反馈方式 |
|------|----------|
| 点击“验证想法” | 按钮变为“分析中...” + 禁用点击 |
| 分析完成 | 页面滚动到报告区 + 按钮恢复 |
| 分析失败 | 在输入框下方显示红色文字说明错误 |
| 设置保存成功 | 按钮短暂变为“已保存”然后恢复 |
| 设置保存失败 | 对应输入框下方显示错误信息 |

### 4.2 加载状态

不搞花哨的骨架屏或进度条。用简单的文字描述当前步骤：

```
分析中...
正在搜索相关讨论...
```

步骤切换时文字变化，给用户“在推进”的感觉。

### 4.3 错误处理

错误信息要告诉用户发生了什么、可以怎么办：

- “API Key 无效，请检查设置中的密钥配置”
- “网络连接超时，请检查网络后重试”
- “未找到相关数据，请尝试更具体的关键词”

不用技术术语，不说“500 Internal Error”。


## 五、组件规范

### 5.1 按钮

| 类型 | 样式 | 用途 |
|------|------|------|
| 主按钮 | 蓝色填充，白字，圆角 6px | 主要操作（验证想法） |
| 线框按钮 | 蓝色边框，蓝字，圆角 6px | 次要操作（生成验证页） |
| 文字按钮 | 蓝色文字，无背景 | 链接类操作（查看报告） |

按钮高度统一 40px，内边距水平 20px。

禁用状态：透明度 0.5，不可点击。

### 5.2 输入框

- 高度 120px（textarea），宽度 100%
- 边框 1px 浅灰，圆角 6px
- 聚焦时边框变蓝色，带 3px 浅蓝外发光
- 内边距 12px
- 字体大小 15px

### 5.3 卡片

- 背景白色，圆角 8px
- 边框 1px 浅灰
- 内边距 20px
- 无阴影（保持扁平）

卡片之间用 24px 间距。

### 5.4 表格/列表

历史记录用简单的列表，每条之间用 1px 浅灰分隔线。

鼠标悬停时背景变极浅灰（#F1F5F9），表示可点击。


## 六、技术实现

### 6.1 技术选型

| 项 | 选择 | 理由 |
|----|------|------|
| 框架 | React 18+ 或 Vue 3+ | 看团队熟悉哪个，功能上没差别 |
| 构建工具 | Vite | 快，配置少 |
| 样式 | Tailwind CSS | 不写 CSS，直接用工具类 |
| 状态管理 | React Context / Pinia | 项目简单，不需要 Redux |
| HTTP 请求 | 原生 fetch | 不需要拦截器那些复杂功能 |

### 6.2 与后端通信

前端只做三件事：

1. 发起调研请求：`POST /api/projects/:id/research`
2. 轮询调研状态：`GET /api/projects/:id/status`（简单轮询，每 3 秒一次）
3. 获取报告：`GET /api/projects/:id/report`

不用 WebSocket，用轮询。简单、可靠、好调试。

### 6.3 数据存储

- 调研历史：存 localStorage
- 当前调研状态：存组件 state
- 设置信息：存 localStorage

不需要 IndexedDB，不需要复杂缓存策略。个人版的数据量根本用不到。

## 七、设计决策记录

这里记录一些做过的取舍，方便后来者理解为什么是这个样子。

**为什么没有登录页面？**

个人版就是单机工具，目标用户是自己用。加了登录就变成“平台”了，心理门槛会提高。等以后做团队版再加。

**为什么没有深色模式？**

深色模式做起来不难，但维护两套配色方案需要额外精力。在验证产品价值之前，不值得花这个时间。

**为什么报告不用图表？**

第一版先用文字和数字展示。图表好看，但需要额外的前端库和数据转换逻辑。如果用户反馈需要图，v1.1 再加。

**为什么没有导出功能？**

同上。用户真需要导出 PDF 的话，浏览器自带打印功能先用着。

**为什么移动端支持有限？**

这个工具的使用场景是在电脑前工作的时候，不是在手机上。移动端保证可读就行，不追求完整交互。


## 八、后续迭代方向

这些是“之后再说”的功能，不是当前必须的：

1. **图表展示**：用 ECharts 或 Chart.js 展示热度趋势、竞品对比
2. **导出报告**：导出为 Markdown 或 PDF
3. **深色模式**：等用户提需求再加
4. **更多数据源配置**：让用户自己添加想监控的网站
5. **团队共享**：等 v2.0 再说
